# 第一轮项目复盘与演进路线

## 为什么先修基础

原项目的界面功能比 README 描述丰富，已经有联机、主题、骰子和排行榜。但服务端将 socket.id 当成长期玩家身份；断线时直接删除玩家，造成刷新丢分甚至房间消失。昵称恢复没有身份验证，任意连接也能请求其他房间转分。结算关闭仅修改本机状态，造成联机显示不一致。历史快照按最新记录向前累计，计算结果也不符合历史时序。

本轮采用随机会话凭证恢复席位。socket.id 只代表当前连接；昵称代表显示名；token 代表设备持有的身份。服务端保存权威状态并广播，客户端不自行修改联机账本。对用户输入的整数范围、玩家关系、成员身份和房主权限分别校验。输出昵称时转义 HTML，服务端仅开放静态资源白名单。

## 可积累的工程经验

1. 数据建模：区分玩家、连接、牌局和流水，避免把临时连接 ID 当成永久身份。
2. 领域逻辑：score-core.js 只负责积分守恒和结算，方便测试以及将来迁移到小程序。
3. 服务端权威：浏览器校验改善体验，服务端校验保证规则，两者都需要。
4. 集成测试：模拟两位玩家加入、权限拒绝、转分、掉线、身份恢复和撤销，使用内存数据库隔离真实数据。
5. 数据生命周期：查看结算保留记录，清零明确操作；长期应将结束牌局归档后再开始下一局。

## 后续阶段

### 第二轮：完整牌局流程

拆分连接 ID 与稳定 playerId；引入 gameId、roundId 和版本号。补充明确轮次、批量记分、备注、牌局归档与历史查询、导入校验、退出与房主移交。联机写操作增加请求 ID 去重、版本冲突检测，避免重试重复记分或重置与新记分竞争。撤销升级为审计事件，保留操作人和原记录。

### 第三轮：体验与维护

模块化拆分页面、存储适配器和网络适配器，优化移动端操作与无障碍弹窗，增加存储失败提示与迁移校验。加入真实浏览器端到端测试、手机实测和 PWA 离线入口。

### 第四轮：小程序与上线

使用小程序原生页面或适合团队的跨端方案，继续复用纯计分规则。后端以稳定用户 ID 绑定微信登录身份，提供清晰 API / 消息协议。上线前完成 HTTPS / WSS、合法域名、房间有效期、限流、数据库备份、日志与监控以及隐私说明。依据上线时的微信平台要求再核实具体配置。

## 本轮取舍与限制

断线保留玩家与房主身份，避免刷新导致自动换房主；所以房主长期离线时需要后续补主动移交。结算建议使用余额匹配，保证积分对平，不保证全局最少转分次数。重置仍清空当前流水，请先导出；JSON 导出是备份资料，暂不提供导入。没有对原数据库做不可逆迁移。

## 本轮页面流程调整

首页仅选择本地 / 联机模式，不再要求个人信息。本地设置默认两位玩家，昵称输入框兼作默认名称提示，可添加到八人，至少保留两人。增删时保留已输入的昵称，空昵称按位置生成默认名称，并检查最终昵称是否重复。

联机页独立设置个人昵称和图案头像。加入按钮左置、房间号输入框右置。入房后可以修改自己的头像昵称，服务端校验成员身份、昵称唯一性和头像范围；同步更新历史显示名称，确保目前按昵称计算的历史快照及撤销兼容。

撤销按钮精简为“撤销”，放在出分提示右侧，暂无记录或联机无权限时禁用。结算页提供 PNG 图片预览和保存，图片包含积分排行、记录数量及结算建议，手机可以长按保存。图片用于分享结果，不是完整账本备份；此前的 JSON 导出入口已替换。

统一系统字体、12 / 16 像素圆角和常用间距，增大积分字号；手机保持两列玩家卡片。使用独立端口与内存数据库进行 UI 检查，避免测试修改真实房间；验证玩家增删上限、默认昵称开局、转分、结算图片生成，以及联机修改资料和刷新恢复。

## 联机闭环完善

玩家 ID 与连接 ID 分离：刷新仅更新 socketId，playerId 和账本关联保持稳定。服务端从当前连接计算在线状态；重启后不会把旧连接误报为在线。记分携带请求 ID，服务端持久化最近请求并去重，返回确认结果，客户端在确认前限制连续提交。

新增房间管理：在线 / 离线 / 已退出状态、复制房间号、主动退出、房主移交、真正解散。离线保留房主身份；主动退出才移交。保留有账目席位，清零释放已退出席位，避免玩家退出破坏积分守恒。所有成员可查看结算结果与导出图片。

标签页使用独立活跃会话，浏览器另外保存最近席位凭证，通过明确的恢复入口找回；同一个席位只能由一个连接持有。旧版房间按需兼容升级，原数据库不做全量清空。测试指南见 ONLINE-TESTING.md，包含同机两标签页和电脑加手机的验收步骤。
